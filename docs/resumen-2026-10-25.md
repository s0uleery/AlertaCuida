## Cifrado de datos personales

Los datos personales se guardan cifrados con **AES-256-GCM**: en la base solo hay valores `v1:…` y por la API se leen normalmente. Se cifra en los adaptadores de la base (`CifradoCampos`); los casos de uso no cambiaron. Detalle en [backend.md](backend.md#cifrado-de-datos-personales).

| Tabla | Columnas cifradas |
|---|---|
| `usuario` | `rut` |
| `paciente` | `rut`, `nombres`, `apellidos`, `fecha_nacimiento`, `direccion` |
| `condicion_paciente` | `descripcion` |

- Un valor alterado, de otra columna o cifrado con otra llave no se descifra: el backend falla en vez de mostrar un dato adulterado.
- Cada valor lleva un vector inicial aleatorio: dos apellidos iguales quedan distintos en la base.
- El RUN se sigue buscando por `rut_hash`, con otra llave (`RUN_CLAVE`).
- **La llave** llega por la variable `CIFRADO_CLAVE` (32 bytes en base64, `openssl rand -base64 32`). Sin ella el backend no arranca. Los perfiles de desarrollo y de pruebas traen llaves propias que no sirven para el servidor.
- **Si se pierde la llave del servidor, los datos no se recuperan.** Hay que guardar una copia fuera del servidor, separada de los respaldos de la base.

Decisiones principales:

- El reloj se identifica solo con su token: nunca envía el id del paciente.
- Las alertas se identifican por el `eventId` del reloj: si se pierde una respuesta por falta de señal, el reloj sigue con el id que ya conoce.
- Los reintentos no duplican nada: todo mensaje que el reloj reintenta lleva un `eventId` único.
- Una lectura mala no traba la sincronización: se descarta sola y se informa.
- Una alerta nunca se rechaza por su contenido; solo si viene mal formada.
- Un aviso rechazado no es un error: responde 200 `RECHAZADO` con el motivo y el reloj pasa al siguiente contacto.
- El reloj acusa cada aviso FCM al recibirlo, para que el servidor lo reintente si no llega.

## API del reloj (tarea 1.4)

Detalle en [backend.md](backend.md#api-del-reloj).

- **Autenticación aparte:** `/api/reloj/**` tiene su propia cadena de seguridad, que solo acepta el token del reloj. Se busca por su hash entre los vínculos vigentes; si el reloj se desvincula, el token deja de servir de inmediato (401 `TOKEN_INVALIDO`). El token del reloj no abre el dashboard, ni el del dashboard la API del reloj.
- **Sincronización:** guarda el estado del reloj, las lecturas (con hora de medición y de recepción), las ubicaciones y los eventos descartados en una sola transacción.
- **Lecturas malas:** se descartan una por una y la respuesta dice cuál y por qué (fuera de rango, hora futura o anterior a la entrega del reloj). Las repetidas se ignoran.
- **Reintentos:** un lote o una alerta reenviados devuelven lo guardado la primera vez, aun si llegan dos a la vez.
- **Errores con código** (`MENSAJE_INVALIDO`, `TOKEN_INVALIDO`, `ALERTA_DESCONOCIDA`, `NO_APLICA`, `LOTE_GRANDE`), para que el reloj sepa qué hacer.
- **Ajustes al contrato:** un lote reenviado responde `loteRepetido: true`; `versionConfiguracion` no viene hasta que exista la configuración del reloj (1.7); 409 `NO_APLICA` si un `eventId` ya lo usó otro reloj.

Código: `AutenticarReloj`, `RecibirSincronizacion`, `RecibirAlerta`, `SincronizacionesJdbc`, `AlertasJdbc`, `IntrospectorTokenReloj`, `SincronizacionesController`, `AlertasRelojController` y `ErroresApiReloj`. Pruebas: `RecibirSincronizacionTest`, `RecibirAlertaTest` y `ApiRelojTest`.
